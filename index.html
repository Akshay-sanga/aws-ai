Domain 1 · Fundamentals of AI & ML

1. AI vs ML vs Deep Learning vs Generative AI

In simple words: AI is the big umbrella (machines acting smart). ML is AI that learns from data instead of hand-written rules. Deep Learning is ML using many-layered neural networks. Generative AI is deep learning that creates new content (text, images, code).
AI  ⊃  Machine Learning  ⊃  Deep Learning  ⊃  Generative AI (Foundation Models / LLMs)

Key points

  • Traditional programming: rules + data → answers. ML: data + answers → rules (a model).
  • Neural network: layers of connected "neurons" (input, hidden, output layers). “Deep” = many hidden layers.
  • Model = the trained artefact. Training = learning. Inference = using the model to predict.
  • Algorithm = the method; model = the result after training on data.
  • Discriminative AI predicts/classifies; Generative AI creates.
  • Common AI tasks: computer vision, NLP, speech, recommendation, forecasting, anomaly detection.
  • When not to use ML: simple deterministic rules suffice, or there is no data / no clear pattern.
Exam tip: “ML is a subset of AI; DL is a subset of ML” appears often. Inference = prediction on new data.

2. Types of Learning & Common Tasks

In simple words: Supervised = learn from examples that already have the right answer (labels). Unsupervised = find hidden patterns without answers. Reinforcement = learn by trial and error with rewards.
TypeDataTasks / examples
SupervisedLabeledClassification (spam/not spam, tumor type) · Regression (house price, temperature – a number)
UnsupervisedUnlabeledClustering (customer segments, K-means) · dimensionality reduction (PCA) · anomaly detection · association
ReinforcementEnvironment + rewardsRobotics, game AI, self-driving, dynamic pricing (agent, action, reward, policy)
Semi-supervisedFew labels + many unlabeledCheaper when labelling is costly
Self-supervisedLabels created from data itselfHow LLMs are pre-trained (predict next word)

Data vocabulary

  • Structured (tables), semi-structured (JSON), unstructured (text, images, audio).
  • Features = input columns. Label/target = what you want to predict.
  • Batch inference (many at once, offline) vs real-time inference (instant, one request).
Exam tip: Number as output → regression. Category as output → classification. No labels, “group” → clustering. “Rewards/penalties” → reinforcement learning.
Domain 1 · Fundamentals of AI & ML

3. ML Lifecycle, Data Quality & Overfitting

In simple words: ML is a loop: get data, clean it, train, test, deploy, watch it, and retrain when it gets stale.

Lifecycle (know the order!)

  1. Business goal / problem framing
  2. Data collection & labeling
  3. Data preparation, EDA, feature engineering
  4. Model training & hyperparameter tuning
  5. Evaluation (on a test set)
  6. Deployment (real-time endpoint, batch, serverless)
  7. Monitoring (drift) → retrain ← this is MLOps (CI/CD for ML)

Key ideas

  • Data split: train / validation / test. Never evaluate on training data.
  • Overfitting: great on training data, bad on new data (memorised noise). Fix: more data, simpler model, regularization, early stopping.
  • Underfitting: bad on both (model too simple). Fix: more features, more complex model, train longer.
  • Bias–variance: high bias → underfit; high variance → overfit.
  • Hyperparameters are set before training (learning rate, epochs); parameters are learned (weights).
  • Data drift / model drift: real-world data changes and accuracy drops → monitor and retrain.
  • Garbage in, garbage out: data quality, representativeness and labelling matter most.
  • Feature engineering = creating/transforming inputs so the model learns better.
Exam tip: “High training accuracy, low test accuracy” = overfitting. Services: Data Wrangler (prep), Feature Store (store features), Ground Truth (labels), Model Monitor (drift).

4. Model Evaluation Metrics (classic ML)

In simple words: Metrics are scorecards. Pick the scorecard that matches the cost of mistakes.

Classification (confusion matrix: TP, FP, TN, FN)

  • Accuracy = correct / total (misleading when classes are imbalanced).
  • Precision = TP / (TP+FP) — “of those I flagged, how many were truly positive?” Important when false alarms are costly (spam filter).
  • Recall (sensitivity) = TP / (TP+FN) — “of all true positives, how many did I catch?” Important when misses are costly (cancer, fraud).
  • F1 = balance of precision and recall.
  • AUC-ROC = how well the model separates classes (1.0 perfect, 0.5 random).

Regression

  • MAE, MSE, RMSE (average error size; lower is better), R² (variance explained).

Business metrics

  • Model metrics must connect to business value: cost savings, conversion rate, customer satisfaction, ROI.
Exam tip: Fraud / disease detection → recall. Fewer false alarms → precision. Predicting a number → RMSE/MAE. Text generation metrics (ROUGE, BLEU) come in Topic 15.

Domain 2 · Fundamentals of Generative AI

7. Generative AI & Foundation Models

In simple words: A foundation model (FM) is a huge model pre-trained on massive general data, which you can adapt to many tasks. An LLM is an FM focused on language. It works by predicting the next token.

Core concepts

  • Transformer: the architecture behind modern LLMs; uses attention to understand context of all words at once.
  • Token: a chunk of text (word or part of a word). Pricing and limits are counted in tokens.
  • Context window: max tokens the model can see (prompt + answer).
  • Embedding: a list of numbers (vector) representing meaning; similar meanings are close together. Used for search, RAG, recommendations.
  • Multimodal: handles several inputs/outputs (text + image + audio).
  • Diffusion models: create images by removing noise step by step (Stable Diffusion, Titan Image Generator). GANs / VAEs: older generative approaches.
  • Model types: text-to-text, text-to-image, image-to-text, embeddings models.
  • FM lifecycle: data selection → pre-training → optimisation (fine-tune/prompt) → evaluation → deployment → feedback.

Pros and cons

AdvantagesLimitations / risks
Adaptability, speed to build, creativity, personalisation, productivity, summarisation, many tasks with one modelHallucination (confident wrong answers), nondeterminism (varied outputs), bias, toxicity, privacy leaks, IP/copyright issues, limited interpretability, outdated knowledge, cost
Exam tip: Hallucination fixes → RAG, better prompts, Guardrails (grounding check), human review. “Guarantees accuracy” is always a wrong option.

8. Amazon Bedrock

In simple words: Bedrock is a menu of top foundation models behind one API. No servers to manage; you pay as you use.
  • Fully managed, serverless; single API for many FMs: Anthropic Claude, Amazon Nova/Titan, Meta Llama, Mistral, Cohere, AI21 Labs, Stability AI.
  • Privacy: your prompts and data are not used to train the base models; data is encrypted; fine-tuned copies are private to you.
  • Key features: Knowledge Bases (RAG), Agents, Guardrails, Model customization (fine-tuning, continued pre-training), Model evaluation, Prompt management, Playgrounds, Batch inference, Provisioned Throughput.
  • Titan models: text, embeddings, multimodal embeddings, image generator.
  • Integrates with IAM, KMS, CloudWatch, CloudTrail, VPC (PrivateLink).
  • Bedrock vs SageMaker JumpStart: Bedrock = simplest, API-only. JumpStart = more control, you host the model on your instances.
  • Choosing a model: task fit, quality, cost, latency, context size, modality, languages, licence/provider.
Exam tip: “Build a GenAI app with multiple FM choices with least overhead” → Bedrock. “Data must not train provider models” → Bedrock guarantees this.

9. Amazon Q, PartyRock & GenAI Business Use Cases

In simple words: Amazon Q is a ready-made AI assistant for work. PartyRock is a free playground to build small AI apps with no code.
  • Amazon Q Business: chat over your company data (S3, SharePoint, Salesforce, Slack, etc. via connectors). Honours existing user permissions. Summaries, Q&A, content generation.
  • Amazon Q Developer: coding assistant in IDE/CLI/console: generate code, explain, debug, upgrade Java, security scan, answer AWS questions.
  • Q in QuickSight: ask business-intelligence questions in natural language. Q in Connect: helps contact center agents.
  • PartyRock: Bedrock-powered playground, no AWS account or coding needed – for learning and prototyping.
  • Use cases: chatbots, summarisation, content creation, code generation, search, translation, image generation, personalization, data extraction, customer-support agents.
  • Business metrics for GenAI: user satisfaction, average revenue per user, cross-domain performance, conversion rate, efficiency, cost saved.
Exam tip: Code help → Q Developer. Internal knowledge assistant → Q Business. Free experimentation without code → PartyRock.
Domain 3 · Applications of Foundation Models

10. Prompt Engineering

In simple words: Prompt engineering = writing better instructions so the model gives better answers, without changing the model.

Parts of a good prompt

Instruction · Context · Input data · Output format/indicator · Persona/role · Constraints.

Techniques

TechniqueMeaning
Zero-shotNo examples, just the task
Single/Few-shotGive 1 / several examples in the prompt (in-context learning)
Chain-of-thoughtAsk the model to reason step by step ("think step by step")
Prompt templatesReusable structure with placeholders
Negative promptsSay what to avoid (common in image generation)
System promptSets behaviour/role for the whole conversation

Best practices

  • Be clear, concise, specific; give context and examples; specify format (JSON, bullets); use delimiters; iterate/experiment.

Prompt attacks (also Domain 5)

  • Prompt injection: hidden instructions override the original ones.
  • Jailbreaking: tricking the model into ignoring safety rules.
  • Prompt leaking / poisoning: exposing system prompt / tainting data.
  • Defence: Guardrails, input validation, least privilege for agents, monitoring.
Exam tip: Prompting does NOT change model weights (fine-tuning does). It is the cheapest first step.
Domain 3 · Applications of Foundation Models

11. Inference Parameters

In simple words: These are dials you turn at request time to change how creative, long or random the output is.
ParameterWhat it does
TemperatureRandomness. Low (0–0.3) = focused, consistent, factual. High (0.8–1) = creative, varied.
Top PChoose from the smallest set of tokens whose probabilities add up to P (e.g., 0.9). Lower = safer.
Top KChoose only from the K most likely next tokens. Lower = safer.
Max tokens / lengthCaps the response size (also controls cost).
Stop sequencesStrings that make the model stop generating.
  • These do not change model weights; they change sampling.
  • Larger context window = can handle longer documents but costs more.
Exam tip: “Consistent, deterministic answers” → low temperature. “Creative brainstorming” → high temperature.
Domain 3 · Applications of Foundation Models

12. RAG, Embeddings & Vector Databases

In simple words: RAG (Retrieval-Augmented Generation) = before answering, the app looks up relevant facts from your documents and pastes them into the prompt. The model answers from those facts, so fewer hallucinations and no retraining.

How it works

  1. Split documents into chunks → create embeddings with an embeddings model (e.g., Titan Embeddings, Cohere Embed).
  2. Store vectors in a vector database.
  3. User asks a question → embed the question → similarity search → fetch top chunks.
  4. Add chunks to the prompt (augmentation) → FM generates a grounded answer (can cite sources).

AWS pieces

  • Knowledge Bases for Amazon Bedrock: fully managed RAG – ingests S3 data, chunks, embeds, stores, retrieves, and cites.
  • Vector stores: OpenSearch Service / Serverless, Aurora PostgreSQL & RDS PostgreSQL (pgvector), DocumentDB, Neptune, MemoryDB; third party Pinecone, Redis, MongoDB Atlas.
  • Use cases: customer-support bots, internal Q&A, up-to-date info, domain-specific answers.
Exam tip: RAG vs fine-tuning – RAG for fresh/changing facts and citations; fine-tuning for style/behaviour/task skill. RAG is cheaper and easier to update.

13. Customizing Foundation Models

In simple words: If prompts and RAG aren't enough, you can retrain the model a little (or a lot) on your own data.
ApproachDataNotes
Prompt engineeringnoneCheapest, instant
RAGyour documentsNo training; up-to-date answers

Domain 3 · Applications of Foundation Models

14. Agents & Guardrails

In simple words: An agent is an AI that plans steps and uses tools to finish a task. Guardrails are safety fences around the model.

Agents for Amazon Bedrock

  • Break a user request into steps (reasoning/orchestration), call action groups (APIs, usually Lambda functions), query Knowledge Bases, and return the final result.
  • Example: “Book my trip and update the CRM” → multiple API calls automatically.
  • Related: Bedrock AgentCore / multi-agent collaboration for building agent systems.

Guardrails for Amazon Bedrock

  • Content filters: hate, insults, sexual, violence, misconduct, prompt attacks.
  • Denied topics (e.g., no investment advice), word filters, PII filters (block/mask), contextual grounding check (detect hallucination & irrelevant answers).
  • Applies to both user input and model output; works across FMs; also via the ApplyGuardrail API.
Exam tip: Guardrails = safety policy layer. Agents = actions/orchestration. Don't confuse with Clarify (bias analysis) or IAM (permissions).

15. Evaluating Foundation Models

In simple words: Check whether the GenAI output is good — automatically with scores, with humans, or with another LLM as judge.
MetricForIdea
ROUGESummarizationWord/phrase overlap with a reference summary (recall-oriented)
BLEUTranslationOverlap of n-grams with reference translation (precision-oriented)
BERTScoreAny textSemantic similarity using embeddings (meaning, not exact words)
PerplexityLanguage modelsHow "surprised" the model is; lower = better
  • Benchmarks: GLUE, SuperGLUE, MMLU, BIG-bench, HELM, WMT.
  • Bedrock Model Evaluation: automatic (built-in/curated datasets), human (your team or AWS-managed workforce), and LLM-as-a-judge. Also RAG evaluation.
  • Judge: accuracy, relevance, robustness, toxicity, fluency, helpfulness, cost, latency.
  • Compare models on your task and data, not only on public benchmarks.
Exam tip: ROUGE = summaries, BLEU = translation, BERTScore = semantic similarity. Memorise.
Domain 4 · Guidelines for Responsible AI

16. Responsible AI & Bias

In simple words: Build AI that is fair, safe, explainable, private and accountable — and keep checking it.

AWS core dimensions of responsible AI

Fairness · Explainability · Privacy & security · Safety · Controllability · Veracity & robustness · Governance · Transparency

Bias & fairness

  • Causes: unrepresentative or historical-biased data, sampling bias, labeling bias, proxy features.
  • Mitigate: diverse/representative data, bias audits (Clarify), balanced datasets, human review, testing across groups, ongoing monitoring.
  • Impact of bias: unfair decisions, legal/reputation harm, loss of trust.

GenAI-specific risks

  • Toxicity, hallucination, intellectual property, plagiarism, deepfakes, misuse, privacy leakage.
  • Mitigate: Guardrails, curated data, watermarks, human-in-the-loop, clear user disclosure.

Selecting models responsibly

  • Consider environmental impact (energy), licensing, safety record, risk level of the use case (high risk = more oversight, e.g., hiring, lending, healthcare).
Exam tip: The answer is almost never “remove humans” — it's “diverse data + testing + oversight + transparency”.
Domain 4 · Guidelines for Responsible AI

17. Transparency, Explainability & Human Oversight

In simple words: Be able to explain what the model is, what data it used, why it decided that, and let a human step in.
  • Transparent = explain how the model works & was built. Explainable = explain individual predictions. Trade-off: simple models (linear regression, decision trees) are more interpretable but often less accurate than complex neural networks.
  • SageMaker Clarify: detect bias before/after training; explainability via feature importance (SHAP); can evaluate FMs.
  • SageMaker Model Cards: document intended use, training data, risks, evaluation.
  • AWS AI Service Cards: transparency docs for AWS AI services (intended use, limits).
  • Amazon A2I: human review workflows for low-confidence predictions.
  • Ground Truth: human labeling incl. RLHF feedback. Model Monitor tracks drift/bias over time.
  • Open source: partial transparency, data lineage, source citation (RAG), documentation, Guardrails.
  • Human-centered design – involve users, make controls obvious, allow feedback.
Exam tip: “Explain why the model denied the loan” → Clarify. “Human validation of results” → A2I. “Document the model for auditors” → Model Cards.

18. Securing AI Systems

In simple words: Same AWS security basics apply to AI: control who can use it (IAM), lock the data (encryption), keep traffic private (VPC), and watch for AI-specific attacks.

Shared responsibility model

AWS = security OF the cloud (hardware, infrastructure, managed service). You = security IN the cloud (data, IAM, configuration, prompts, applications).

Domain 3/5 · Cost & Deployment Choices

20. Cost, Pricing & Deployment

In simple words: GenAI is billed mostly by tokens. Smaller model, shorter prompt, and batch processing all save money.

Bedrock pricing options

  • On-demand: pay per input/output token (or per image). No commitment. Best for variable/testing.
  • Batch: submit many prompts for asynchronous processing at a discount.
  • Provisioned Throughput: reserve model units (hourly; optional 1- or 6-month commitment) for steady high load; required for custom models.
  • Customization has training cost + storage; RAG has embedding + vector store cost.

Reduce cost

  • Right-size model (smaller if quality is enough), shorter prompts, cap max tokens, cache, batch, prompt-engineering/RAG before fine-tuning.

Hosting trade-offs

  • Self-hosted (SageMaker) = control, but you pay for instances even when idle. Serverless/managed (Bedrock) = pay for use.
  • SageMaker inference: real-time, serverless, asynchronous, batch transform.
  • AWS Trainium (chips for training) and AWS Inferentia (chips for inference) give better price-performance than GPUs.
  • Other tradeoffs: responsiveness/latency, availability, redundancy, Region coverage, performance vs cost, token-based pricing, custom-model cost.
